# 编排与规划：怎么判断

`SKILL.md` 只列流程；这里是阶段二（编排）和阶段三（规划）要做的判断，以及生成器替你防住了什么。

## 阶段二 · 四类决策

这一段是**人和智能体一起做判断**，工具只提供证据。

| 决策 | 依据 | 怎么落实 |
| --- | --- | --- |
| **定边界**：这些场景该做成几份 skill | ① 有没有共同入口采集 ② 根因是否重叠 ③ 规模到顶就停（见下） | 一份清单一份 skill；装不下就再导一份清单 |
| **合并**：同一故障被多来源各写一遍 | `list` 已自动归并同名；`--suggest-merge` 给候选并比对双方的修复动作 | 多个 `--entry`，或把它们写进同一个场景 |
| **拆分**：一组里混了两类故障（如"中断"和"震荡"） | `--show-causes` 看根因是否分属两个技术域 | 拆成两个场景，各自 `--unit` / `--entry` |
| **剔除（自动）**：案例特定内容、没有判据也没有修复的原因 | 默认就剔除并记录；`plan` 会列出剔除清单 | 需要保留时才加 `--include-example-specific` / `--keep-undecidable` |
| **剔除（人工）**：同一单元里混进来的跨领域内容（查 ISIS 却混进 MPLS/BGP/组播） | `list --show-causes` 看根因清单，挑出不属于本场景的 | 场景清单的 `exclude`（只作用于该场景）或 `--exclude`（全局），写 `node_id` 或名称关键词 |

判断完把编排固化成场景清单：`list --export-scenarios scenarios.json`，然后编辑——填技能名 `name`、
每个场景的英文 `slug`（它的 `reference/` 文件名）、拆并 `entries` 与 `units`、删掉不要的场景。
清单格式见 [`cli.md`](cli.md#例子)。

### 聚合边界（参考值）

**一份 skill 装 5–7 个场景、30+ 根因、3–7 条公共前置、约 500 行。**
`plan` 会逐项对照着报，但**只报不拦**——超出不是错误，是交付时要说明、或回来再编排一轮的信号；
数据本身撑不到 30 个根因时，如实做小的那份，不要为凑数硬并。
一个上百症状的子图不是一份上百章节的文档，而是**十几份这样的 skill**。按顺序判：

1. **有没有共同入口采集**（能不能同一份）：`plan` 里公共前置塌到 0–1 条，就是这些场景没有
   共同入口——一份 skill 的形态是"先公共采集、再按跳转表分流"，没有共同入口就别硬凑。
2. **根因是否重叠**（该不该同一份）：`--suggest-merge` 的重叠度；根因互不相干的两组放一起，
   跳转表只是个目录，没有分流价值。
3. **规模到顶就停**：场景数 / 根因覆盖 / 文档规模任一超了，就另起一份清单。

主题名（"设备硬件"）是前两步的**结果**，不是判据：先验按主题分会把共用 `display fan` 的
高温与风扇故障拆开。**也别用"主症状进正文、其余列成附表"绕过边界**——附表里的症状没判据、
没根因对照，读者走不下去；超出的场景名字进不了 description，agent 不会为它选中这份 skill，
正文有、检索不到等于没覆盖（模板检查会告警）。

### 无关的点和边

跨诊断单元的靠 `--unit`、案例特定的默认剔除、跨故障的靠边语义（`refers_to` / `leads_to`
指向另一个故障入口，选图默认不跨越）。剩下**同一单元里的跨领域内容**机器判不了，就是人工活：
`exclude` 把该节点及其所有边整条剔掉（原因带着它的检查、观测、修复一起走），在 `plan` 与构建
输出里逐条记账；写错的关键词直接报错，不会静默漏掉。

## 阶段三 · 读 `plan`

**先 plan 再 build。** `list` 数的是图上有什么，`plan` 数的是**文档里实际会有什么**——
剔除、按命令去重、按名称折叠根因都已经算进去了。

```
| 场景 | 步骤 | 根因 | 修复命令 | 复用的公共前置检查 |
| 场景A：IS-IS 邻居无法建立 | 4 | 4 | 4 | 步骤 1、步骤 2 |
| 场景B：协议邻居关系无法建立 | 3 | 3 | 0 | 步骤 1 |
| **合计** | **7** | **7** | **4** | 公共前置检查 2 条 |

还能再合并的地方（只是提示，合不合由你判断）：
  - 场景B 的 3 个根因全部也出现在 场景A，可考虑并入（合并后少一个场景）
  - 同一个根因在多处各排一遍：场景A 的「检查MTU不一致」；场景B 的「检查MTU不一致」
```

看这几件事，不满意就回阶段二改清单再 plan：

1. **每个场景的步骤数**：明显偏厚（一个场景就占掉全篇一半）多半还能拆；只有 1 步且修复命令为 0
   的场景考虑并掉或不做。单条阅读路径超过 25 步模板检查会告警。
2. **修复命令数为 0 的场景**：生成出来只能定位不能处置，要么先不做，要么交付时说清楚。
3. **合并提示**：根因被完全包含 → 并；同一根因在多个场景各排一遍 → 说明场景边界画错了。
4. **公共前置的规模**：塌到 0–1 条或居高不下都说明边界画错了（门槛默认 80%，`--shared-coverage`
   可调；单故障 skill 里同一条门槛按排查步骤算）。
5. **剔除清单**：逐条看"未进入正文的条目"——自动剔除的对不对、还有没有跨领域内容漏网。
   漏网的加进 `exclude` 再 plan 一次；`plan --exclude "MPLS"` 可以先试效果再写进清单。

`plan` 末尾的**交付统计**（步骤:根因、判据密度、命令复用率、复检覆盖率……）健康值与含义见
[`cli.md`](cli.md#交付统计)。超出健康值的项 `build` 会再提醒一次：**要么回到对应阶段再做一轮，
要么交付时说明**，不要默默放过。

## 批量生成时，让几份 skill 互相认得

图里 `refers_to` / `leads_to` 是来源自己画的那条线——**两份 skill 之间唯一有来源的接缝**。
生成器把它写成转向留在根因对照表（根因级在它自己那行，症状级在「未找到根因」兜底行）；
要带上目标 skill 的名字，就得让它知道这一批都生成了什么：`build --each` 自己算；一个子图跑一次
`build` 时用 `--skill-index names.json` 传进去。

没有索引就只写故障名；给了索引却没覆盖到的目标写成「本批次未生成对应 skill」并告警——
这是真缺口，要么补生成那份，要么交付时说清这条线索到此为止。转向也归后校验管，且更严：
**目标是图里存在的症状还不够，必须真有一条边指过去**。写法见
[`output-spec.md`](output-spec.md#跨-skill-的转向)。

## 生成器替你防住的烂输出

| 症状 | 处理 |
| --- | --- |
| 同一条命令重复几十次 | 前置检查按命令合并，步骤写"复用前置检查步骤 N 回显"；缩写与全写认作同一条，保留全写、另一种写法登记为"来源另有写法" |
| 单故障 skill 里同一条命令每步下发一遍 | 被 ≥80% 步骤读到的提成公共前置采一次；某条回显只指向一个步骤时进 `## 步骤跳转表` |
| 公共前置里混进少数场景才用的命令 | 只有分流前必须跑的留在公共前置并标出适用场景（覆盖率 ≥ 80%、或决定跳哪个场景、或采集期就判根因）；其余下沉成各场景的「本场景采集」 |
| 步骤里出现 IP、设备名、拓扑 | `example_specific` 条目默认剔除并记录；保留时标出案例字面量 |
| 命令里写死某台设备的取值（`slot 3`） | 命令旁标「注意：命令含示例取值（…），按现场实际替换」并告警；**不替换、不改名** |
| 几十个步骤、长度爆炸 | 按诊断单元切分场景；`--max-steps` 兜底；>25 步告警 |
| 场景杂糅（ISIS 里混进 MPLS/BGP） | `--unit` 收窄；选图不跨 `refers_to` / `leads_to`；剩下的用 `exclude` 人工剔除 |
| 同一故障被拆成几份薄 skill | 按故障跨来源归并（手册 + 作战树 + 案例库），同名根因折成一步、判据与修复取并集 |
| 名字不同实为一事 | `list --suggest-merge` 按根因重叠找候选，再比对双方的**修复动作**——修复相同才该合 |
| 回显、表格、正文句子被当成命令或根因 | `Peer : <ip>`、`1.3.1 4 100 0 Connect 0`、「但由于…存在Hash问题」按形状识别并剔除，理由列在构建输出里 |
| 判据没有区分力 | 一条判据被同场景三步以上共用、正反判据跳同一处——报 ERROR |
| 参数填不出来 | 来源示意图的设备编号（`device B`）报 ERROR；没被命令引用的入参告警 |
| 润色时补出图里没有的命令/根因 | 后校验逐条回查原图，没来源的报 ERROR |
| 批量生成的几份 skill 互不相认 | `refers_to` / `leads_to` 写成转向留在根因对照表（见上） |
