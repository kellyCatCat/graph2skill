# 产出 skill 的模板规范（硬性）

生成的每一份 skill 都必须符合本规范。四个章节顺序固定、缺一不可。

一份 skill 可以是**单故障**（一个 symptom 入口），也可以覆盖**多个故障场景**——后者共用一套
前置检查，用「场景跳转表」分流，每个场景一组独立编号的步骤。两种形态的差别只在
`# 前置检查` 末尾和 `# 排查步骤` / `# 根因对照表` 的内部结构，四个一级章节始终不变。

## 文档头部

```
---
name: skill-name-in-English（例如：arp-learning-failure）
description: 故障现象 + 适用时机。例：基站掉站。出现掉站/站点不通/链路 Down 告警时使用。
---
```

`name` 必须是英文 slug（`^[a-z0-9-]+$`）。图谱里的症状名多为中文，**无法机械翻译**，
由调用方（智能体或人）给出，不要自动音译。

## 章节

从一级标题开始，每级增加一个 `#`：`# 入参列表` → `# 前置检查` → `# 排查步骤` → `# 根因对照表`，
排查步骤内每一步写成 `## 步骤N：步骤名称`。

### 1. `# 入参列表`

| 信息 | 是否必填 | 说明 |
| --- | --- | --- |

- 「信息」列写参数的可读名称，**去掉空格和连字符后要能和 CLI 里的参数名对上**
  （`<endpoint-ipv6>` ↔「endpoint IPv6」，`<color-id>` ↔「color」）。
- 只能从回显里读出来、用户提供不了的参数，「是否必填」写「否」，并在说明里注明来自哪一步。

### 2. `# 前置检查`

有序列表，每条给出 CLI 命令与采集内容；能在采集阶段就判定的根因，写一行「根因定位」。

- CLI 之间必须是**分步骤的线性执行关系**，不可以有内部跳转。
- 所有 CLI 的参数**不可以超出入参列表中的必填项目**。
- 多个场景共用前置检查时，同一条命令只写一次，采集内容取各场景所需的并集。

```
1. **查询目标 SRv6 TE Policy 状态**
   - CLI 命令：`display srv6-te policy endpoint <endpoint-ipv6> color <color-id>`
   - 采集内容：`Policy State`、`List State`、Segment List ID 与 Policy 名称。
   - 根因定位：若回显为空或提示该 Policy 不存在，判定根因为“SRv6 TE Policy 不存在”，结束排查。
```

#### 场景跳转表（仅多场景时）

公共前置检查之后、`# 排查步骤` 之前，用二级标题 `## 场景跳转表` 给出分流表，三列固定：

```
## 场景跳转表

公共采集做完后，按下表判据进入对应场景；判据都不命中时逐个场景排查。

| 前置检查步骤 | 判据 | 跳转场景 |
| --- | --- | --- |
| 步骤 5（`display isis peer verbose`） | 邻居状态为 `Down` 或邻居列表为空，且**无**邻居中断/震荡类告警 | → **场景A：IS-IS 邻居无法建立** |
| 步骤 6（`display alarm active verbose`） | 存在 `isisAdjacencyChange` 告警 | → **场景B：IS-IS 邻居震荡** |
```

- 「前置检查步骤」必须指向真实存在的前置检查序号，并附该步的命令。
- 「判据」用反引号标出字段与取值；来源没有可判定的回显判据时，如实写
  “（来源未给出可判定的回显判据）按现象与告警匹配：…”，不要编一个判据出来。
- 「跳转场景」必须与下面的 `### 场景X：名称` **逐字一致**。
- 每个场景至少要在表里出现一次；表里也不允许出现不存在的场景。

### 3. `# 排查步骤`

默认顺序执行。**单故障**时每步用 `## 步骤N：名称` 作标题；**多场景**时先用
`### 场景X：名称` 分节，节内每步用 `#### 步骤N：名称`，**每个场景的步骤从 1 单独计数**，
「顺序执行步骤 N」指本场景内的第 N 步。四类信息写成有序列表：

```
## 步骤4：检查 SRv6 TE Policy 是否被 shutdown

1. **步骤名称**：检查 SRv6 TE Policy 是否被 shutdown
2. **CLI 命令**：`display srv6-te policy endpoint <endpoint-ipv6> color <color-id>`（查看 `Policy State` 字段）
3. **跳转信息**：
   - `Policy State` 不为 `Down (Shutdown)`：顺序执行步骤5。
   - `Policy State` 为 `Down (Shutdown)`：定位根因，结束排查。
4. **根因定位**：
   - SRv6 TE Policy 被 shutdown
```

需要额外下发命令时，「CLI 命令」下列多条并注明触发条件（`（仅当 X 为 Y 时执行）`）。

- 步骤编号从 1 开始连续（多场景时按场景各自从 1 开始）。
- 判据来自前置检查已采集的回显时，注明“复用前置检查步骤 N 回显”或“查看 X 字段”，**不要重复下发同一条命令**。
- 跳转信息：判据字段与取值都用反引号标出；“跳转步骤 N”里的 N 必须真实存在，
  落到下一步时写“顺序执行步骤 N+1”。**最后一步**要写清全部判据都不命中时的去向：
  判定「未找到根因」，输出已执行的全部检查步骤及结果摘要，结束排查。
- 根因定位：**只给根因名称**，不写修复动作和复检命令（它们统一放在根因对照表）。本步骤不产生根因时写“无”。

### 4. `# 根因对照表`

单故障时一张表；多场景时按 `### 场景X：名称` 分节，每节一张表，列固定为四列：

| 根因 | 现象 | 修复CLI和方法 | 复检命令（可选） |
| --- | --- | --- | --- |

- 「根因」列的文字要和排查步骤「根因定位」里写的名称**逐字一致**。
- 「现象」写判定这个根因所依据的字段与取值。
- 「修复CLI和方法」照抄来源给的说法，不要展开、不要补全；来源为空时写“无直接修复CLI”并说明只能定位。
  影响性大的修复注明影响与建议的操作时机。
- 「复检命令（可选）」照抄来源给的复检说法，没有复检手段时留 `-`。
- 全部步骤走完仍未命中任何故障特征时，加一行「未找到根因」，「修复CLI和方法」写
  “输出已执行的全部检查步骤及结果摘要”。

## 命令行约束

**最重要的一条：只能使用源数据里出现过的 CLI，一条都不许自己生成。**

在知识图谱里，可用的命令来源只有：`check` / `repair` / `escalation` 节点的
`attrs.command_templates`，以及 `attrs.procedure` 里的文字说法。

- **`observation` 不是命令来源**。回显是某台设备当时的输出，里面的 `bgp 100`、`peer 1::2 enable`
  是那台设备的现状，不是配置模板。
- 来源只给了一句修复方向（如“减少 policy 数量”“BGP 视图下配置 ipv6-family sr-policy”），
  就照实写这句方向，**不要补全成可执行的配置序列**——补出来的命令没有依据，
  在真实设备上多半是错的，而 agent 会当真执行。
- 来源那一格是空的，写“无直接修复CLI”并说明只能定位。

其余格式约束：

- 命令一律用反引号包成行内代码；多行配置序列用围栏代码块或表格内 `<br>` 分行。
- 可变参数一律用尖括号 `<>`，不要用 `{}`、`[]`、`XXX` 或大写占位符。
  来源里写成 `{interface-type}` 的，只规整分隔符成 `<interface-type>`，**不改名字**。
- 参数名沿用来源写法，不要翻译、不要换词；同一个参数在整篇 skill 里必须用同一个名字。
- 接口名使用全称（`GigabitEthernet0/1/0`，不写 `GE0/1/0`）。

## 自检

生成后跑 `python3 scripts/build_skill.py lint <skill 目录>`：
四章节顺序、步骤编号连续（多场景时按场景各自计数）、跳转目标存在、
场景跳转表与 `### 场景X` 一一对应、根因名称在所属场景的对照表里逐字可查、
CLI 参数都在入参列表内、占位符写法、命令是否有来源——都会被检查。
