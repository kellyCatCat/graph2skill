# 图谱字段 → 四章节的映射

模板本身见 [`skill-template.md`](skill-template.md)。这一页说明生成器**怎么把图谱字段填进四章节**，
便于核对产物、或在数据缺失时判断该写什么。

**一份 skill 覆盖一个子图**：图里的每个故障成为它的一个场景。一个故障 = 一个 `symptom` ×
一个诊断单元，加上该单元内向前可达的原因、检查、观测、修复、升级节点（并把 `supports` /
`confirms` / `excludes` 这些指回原因的判据边拉回来）。诊断单元来自边的
`diagnostic_context.section`；不切分就会把同一症状在几十个章节与案例里的原因合成一个场景，
那正是几十步、场景杂糅的来源。

场景从哪来：`build` 不给 `--entry` 时用自动分组（和 `list` / `plan` 同一套），给了场景清单
（`--scenarios`）就用清单里的编排。`--entry` 只做其中一个故障，`--each` 则是每个故障各自
独立成一份 skill。

生成前用 `plan` 预览这些规则作用后的实际规模（步骤/根因/修复命令数），不必先写盘再看。

## 合并与剔除规则

| 情况 | 处理 |
| --- | --- |
| 多个 check 节点跑同一条命令 | 前置检查按命令签名合并成一条（缩写与全称折叠），标题取首个，采集内容取并集 |
| 单场景时，一条命令被 ≥80% 的排查步骤用到（`--shared-coverage`） | 提成公共前置采一次，各步骤写“复用前置检查步骤 N 回显”；挂在原因下的检查也算，否则同一条命令每步下发一遍 |
| 单场景时，一条采集只有一个步骤读、又不决定分流 | 还给那个步骤自己下发——留在公共层等于让走别的步骤的读者白敲一条命令 |
| 单场景时，某条回显只指向一个步骤 | 进 `## 步骤跳转表`，读者采完直接进那一步；指向多个步骤的回显分不了流，不进表 |
| 多场景时，一条采集的场景覆盖率低于门槛（默认 80%，`--shared-coverage` 可调） | 不进公共前置：**读它的每个场景**各拿一份，渲染成该场景的「本场景采集」，步骤改写成“复用本场景采集 N 回显”。两者的代价不对称——留在公共层是让不相干的读者在真设备上多敲命令，下沉只是文档里多几行、而读者只看自己那一节。例外是它的读数决定分流（场景跳转表引用它）或它在采集阶段就判定根因：那两种读者必须在分流前跑，留在公共前置并标出「适用场景」 |
| 步骤的判据来自某条前置检查的回显 | 步骤不重复下发命令，写“复用前置检查步骤 N 回显（检查名，查看 `字段` 字段）” |
| 前置检查既没人引用、又不判定根因 | 从文档里剪掉（引用编号会自动重排） |
| 节点 `example_specific=true` | 默认剔除，在构建输出的「未进入正文的条目」里逐条说明；`--include-example-specific` 可保留，保留时命令旁标出案例字面量（IP、设备名、具体接口号、System ID） |
| 原因既无判定观测又无修复动作 | 默认剔除并记录原因；`--keep-undecidable` 可保留 |
| 超过 `--max-steps` | 剔除并记录，不静默丢失 |
| 人工判定与本场景无关（`exclude`） | 该节点及其所有边整条剔除，在构建输出里逐条列出；匹配不到时报错而不是静默跳过 |
| `refers_to` / `leads_to` 指向的另一个故障入口 | 选图时不跨越展开（那是另一个故障），但写成**转向**留在根因对照表里：读者走到这一行时需要知道下一步去哪。详见下面的「跨 skill 的转向」 |
| 多个来源写同一个故障（症状名归一后相同） | 合并成一份：入口检查按节点去重、原因按名称折叠、判据与修复取并集、触发说法与必填槽位取并集 |
| 合并后同名根因的修复挂在另一个来源的节点上 | 修复按**折叠后的原因**查找，不按判据所属节点，否则会误报“无直接修复CLI” |

## 产物

交付的是**整个 skill 目录**（`reference/` 也是 skill 的一部分）——**子图不对外暴露**：

```
out/isis-neighbor-down/              # 单故障：一个文件
└── SKILL.md                # 四章节，不放出处

out/bgp-troubleshooting/             # 多场景：入口 + 每个场景一份
├── SKILL.md                # 入参列表 / 前置检查（含场景跳转表）/ 排查步骤（参考文件表）
└── reference/
    ├── neighbor-down.md    # # 场景A：… + # 根因对照表
    └── route-flap.md       # # 场景B：… + # 根因对照表
```

输出目录里不会有别的东西：出处不进 skill，要核对就用 `check --graph` 回查原图。

多场景为什么拆文件：**读者只走一个场景**。步骤都留在入口文件，命中这份 skill 的每个读者
都要加载别人那几份；拆出去之后入口只剩分流所需的部分。这和公共前置的取舍是同一件事
（留在公共层 = 让不相干的读者多敲一条命令），只是低了一层。单场景不拆——跳转表只有一行、
文件只有一个，纯属多一层间接。

frontmatter 的 `description` 由症状生成：`name`（+ `attrs.abnormal_behavior`）作故障现象，
`aliases` + `attrs.match_phrases` 作适用时机，`attrs.trigger_context` 作补充；
`name` 必须由调用方给出英文 slug。

## 三种“合并”的边界

| 按什么合并 | 用在哪 | 为什么 |
| --- | --- | --- |
| **症状（跨来源）** | 决定 skill 边界，自动 | 手册 / 作战树 / 案例库写同一个故障，拼写归一后同名即合并 |
| **命令行** | 只合并前置检查里的采集步骤，**不作为 skill 边界** | 命令是手段不是故障：`display isis peer` 横跨十几个故障，按它聚类就是场景杂糅 |
| **根因** | 文档内同名折叠（自动）；跨故障只作为合并**建议**（`list --suggest-merge`） | 名字相近不等于同一根因——「MTU 两端不一致」与「MTU 小于 Hello 长度」判据和修复都不同，自动合并会把两种修复混在一起 |

模板检查会对同一份文档里写法高度相似的根因给出提醒（不是错误），供人决定要不要在源图里治理。

## `# 入参列表`

| 来源 | 是否必填 | 说明列写什么 |
| --- | --- | --- |
| `symptom.attrs.required_slots` | 是 | 现场提供。先去掉抽取哈希再归一：`peer ip c8be5e6454`、`peer_ip_9d10bb2201` 都是 `peer ip` 一行；只剩哈希的槽位当伪参数剔除并记录 |
| 前置检查命令里的 `<token>` | 是 | 前置检查步骤 N 命令参数 |
| 只在排查步骤命令里出现的 `<token>` | 否 | 从前置检查回显中提取，无需人工输入 |
| 只在修复/复检命令里出现的 `<token>` | 否 | 修复动作参数，按现场规划或回显确定 |

「信息」列由参数名把 `-` / `_` 换成空格得到（`<interface-type>` →「interface type」），
所以去掉空格和连字符后仍与 CLI 参数名一致；中文参数名原样保留。
同一参数按“去空格、去连字符、小写”归一，槽位与 CLI 参数会合并成一行。

## 单故障 vs 多场景

| | 单故障（`--entry`，或子图里只有一个故障） | 多场景（默认：整个子图一份） |
| --- | --- | --- |
| 前置检查 | 该故障的入口检查，按命令去重 | **所有场景**的入口检查，按命令跨场景去重 |
| 跳转表 | 无 | `## 场景跳转表`：前置检查步骤 / 判据 / 跳转场景 |
| 文件 | 只有 `SKILL.md` | `SKILL.md` + `reference/<场景 slug>.md`，一个场景一份 |
| 排查步骤 | `## 步骤N`，就在 `SKILL.md` 里 | `SKILL.md` 里只留一张「场景 / 参考文件 / 内容」表；步骤在各自文件里写 `## 步骤N`，**每个场景从 1 计数** |
| 根因对照表 | `SKILL.md` 末尾一张表 | 每份参考文件末尾各一张，只含本场景的根因 |
| 参考文件名 | — | **必须有语义的英文 slug**（`neighbor-down.md`，不是 `scenario-a.md`）。中文场景名无法机械翻译：自动分组时用 `--names` 的 `{node_id: slug}`，用清单时在场景里填 `slug`；缺了就拒绝生成，模板检查 也会把占位名报成 ERROR |
| 跳转"顺序执行步骤 N" | 全文唯一编号 | 指本场景内的第 N 步 |

跳转表的判据取各场景入口检查能观测到的表达式；子图没给可判定的回显时，
如实写“（来源未给出可判定的回显判据）按现象与告警匹配：…”，不编判据。

## `# 前置检查`

来自 `symptom -diagnosed_by-> check`，以及 `symptom -next_step-> check` 及其 `next_step` 链
（最长 6 步，遇环即停）。每条：

- **CLI 命令**：该 check 的 `attrs.command_templates`（`{x}` 规整为 `<x>`；`[x]` 是命令行的可选参数写法，保持原样）；来源没有命令模板时
  写“来源未给出命令模板，按来源步骤说明人工采集”。
- **采集内容**：`attrs.intent` + 该检查可能观测到的 `attrs.field` 字段名；两者都没有时用 `attrs.procedure`。
- **根因定位**：只在该观测判定的原因**没有自己的排查步骤**时才写，避免同一根因判两遍。
- **执行条件**：引出这条检查的 `diagnosed_by` / `next_step` 边带条件时写，`〔条件：…（未求值）〕`。

## `# 排查步骤`

每条 `symptom -has_cause-> cause` 一步，顺序按边的 `rank`：

| 模板要求 | 数据来源 |
| --- | --- |
| 步骤名称 | `检查<原因名>` |
| CLI 命令 | 判据观测由某条前置检查产生 → “复用前置检查步骤 N 回显（检查名，查看 `字段` 字段）”；否则用该原因 `diagnosed_by` 检查的命令模板 |
| 跳转信息 | `confirms` / `supports` 观测 → “定位根因……结束排查”；`excludes` 观测 → “排除根因……顺序执行步骤 N+1”；末尾补“以上判据均不命中”一行 |
| 根因定位 | 该步骤能判定的原因名 |
| 适用条件 / 执行条件（可选子项） | `has_cause` 边的条件写在「步骤名称」下；该原因 `diagnosed_by` 边的条件写在「CLI 命令」下 |

- `supports` 判定的根因一律带“（仅支持性证据 `supports`，需人工确认）”。
- 判据边带条件时，条件写在冒号之后：`` `判据`：〔条件：…（未求值）〕定位根因“…” ``。
- 最后一步的兜底写“判定‘未找到根因’，输出已执行的全部检查步骤及结果摘要，结束排查”。
- 原因没有任何判据观测时，跳转信息写“本子图未给出该原因的判定观测”，仍把它列进根因定位，
  对照表里的现象列注明“本子图未给出判定观测”。

## `# 根因对照表`

汇总前置检查与排查步骤里出现的全部根因，外加一行「未找到根因」。

| 列 | 数据来源 |
| --- | --- |
| 根因 | `cause.name`，与「根因定位」逐字一致 |
| 现象 | 判定该原因的观测表达式（优先 `normalized_expression`）+ 判据边的条件 + 证据强度标注 |
| 修复CLI和方法 | `cause -repaired_by-> repair` 的 `command_templates`（边带条件时紧跟其后）；没有命令就照抄 `procedure` 文字；都没有写“无直接修复CLI”。再依次写 `preconditions` 作“前置条件”、`service_impact` 作“影响”、`rollback` 作“回退”，缺的几项合成一行“来源未给出：…” |
| 复检命令（可选） | 仅当 `repair -next_step-> check` 存在时取该检查的命令（边带条件时紧跟其后）；否则 `-` |

多条命令在表格内用 `<br>` 分行。

### 跨 skill 的转向

一个子图一份 skill，读者迟早会走到这份文档管不了的地方。图里 `refers_to` / `leads_to`
就是来源自己画出的那条线——**两份 skill 之间唯一有来源的接缝**。它们不参与选图展开
（跨过去就是另一个故障，正是场景杂糅的来源），但会写进根因对照表：

| 边 | 写在哪一行 | 渲染成 |
| --- | --- | --- |
| `cause -leads_to-> symptom` | 该根因自己那一行的「修复CLI和方法」 | `转向故障：「<症状名>」（skill: <slug>）——该根因会引发此故障，处置后复查` |
| `cause -refers_to-> symptom` / `escalation` | 同上 | `转向故障：「…」` / `转交：「…」——来源把这里转向该处` |
| `symptom -refers_to-> symptom` / `escalation` | 「未找到根因」兜底行 | 同上；边上有 `condition` 时附 `〔条件：…（未求值）〕` |

`leads_to` 落在另一个 `cause` 上**不算转向**：那是本图内的传播，不是另一份 skill。

`（skill: <slug>）` 从哪来：

- `build --each`：先把整批的 slug 全定下来再逐份写盘，自己就知道（先生成的那份否则不知道
  后生成的那份叫什么名字）。
- 分开跑的 `build` / `build --scenarios`：用 `--skill-index`，格式与 `--names` 相同的
  `{node_id: slug}`。
- **一个 slug 都没有时只写故障名，不写 skill 子句**——生成器此时并不知道有没有别的 skill，
  替它断言“没有生成”是在编造一个不存在的批次。
- 有索引但没覆盖到目标：写 `（本批次未生成对应 skill）`，模板检查同时告警。这是真缺口：
  要么补生成那份 skill，要么交付时说清楚这条线索到此为止。

转向绝不写成反引号代码：后校验把代码片段当命令回查，写成代码的 slug 会被报成编造的命令。
括号内用 `，` 分隔也是同样原因——后校验按 `；` 切片段，用了它转向就会被切成两半。
